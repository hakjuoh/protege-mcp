# 0.8 asynchronous job runtime

- Status: accepted for implementation
- Date: 2026-07-20

## Context

The current tool guard, principal lease, and audit ticket span one synchronous handler. Returning a job id while
detached work continues would otherwise escape capability revocation, misreport audit completion, and allow a
generic `start_job` permission to dispatch higher-privilege work. Jobs also need one deterministic answer to
cancel-versus-commit and restart behavior.

## Decision

### Contract and types

0.8.0 job types are `classification`, `project_qc`, `semantic_diff`, and `inference_materialization`. Existing
synchronous tools remain. The runtime is live-plugin-only; short-lived CLI processes do not issue job ids.
Core owns `JobDescriptor`, `JobInputIdentity`, `JobError`, `JobArtifact`, the state machine, clocks, cancellation,
quota decisions, and scheduler interfaces. Plugin owns per-window workers, principal/revocation integration,
live snapshot capture, and EDT commit.

`JobInputIdentity` contains complete model revision, ontology/import-closure fingerprint, policy digest,
preflight-asset and import-lock digests, mapping revision, exact reasoner/configuration digest, normalized
request digest, and captured byte/provenance digests for every secondary semantic-diff input. Inputs are captured
once and never refetched. From acceptance for 15 minutes, same owner/workspace/type/idempotency-key plus the same
input identity returns the existing job; the same key with different identity is `idempotency_conflict`; a new
key creates a new job even for equal content. Terminal and cancelled jobs obey the same rule until expiry.

### Ownership and dynamic authority

A job is owned by exact workspace id plus principal subject/client/grant fingerprint. Token refresh within the
same grant retains ownership. Re-consent/re-grant creates a new fingerprint that cannot see the old jobs; old
grant revocation cancels them. Only that owner can list,
get, cancel, or export it; every mismatch returns the same `unknown_job` response as absence. The start handler
resolves required capabilities from job type and destination. The worker retains a revocable execution lease,
subscribes to owner revocation, and reacquires dynamic authorization before every publication. Interactive
confirmation applies only to ontology/filesystem mutation and explicit artifact export. Revocation, expiry,
window close, or server shutdown requests cancellation.

### State and bounds

Legal states are `queued`, `running`, `cancel_pending`, `succeeded`, `failed`, and `cancelled`; the normative
transition table is PLAN.md §6.2. CAS rejects every other transition and terminal states are immutable. A failure
after `cancel_pending` is diagnostic and ends `cancelled`. Cancellation is idempotent. Executor rejection is
terminal `failed/job_queue_full`. Two workers and a 32-entry queue serve one backend; quotas are eight active and
32 retained jobs per principal, 128 retained per backend, one-hour terminal retention, 100 rows per list page,
and bounded monotonic progress. Each job may own four artifacts, 64 MiB each/128 MiB total, 1 MiB result JSON,
and 128 MiB staging; backend staging is 512 MiB, progress text is 1 KiB, and cancellation grace is five seconds.
Async reasoning accepts only exact profiles whose live cancellation test proves bounded stop/disposal within
that grace; otherwise start fails with `job_reasoner_not_cancellable`.

Jobs are in-memory and non-persistent. A closed window or backend/broker restart cancels/disposes the runtime,
deletes unexported staging, and makes all former ids unknown. No instance adopts another runtime's mutable jobs.

### Cancellation and publication linearization

Each job owns a monotonic cancellation tombstone and short exclusive commit permit. Compute/private staging is
discardable. Cancel/revoke/expiry/shutdown CASes the tombstone without waiting. The worker completes blocking
confirmation first, enters the permit, rechecks tombstone, revocation, expiry, input/policy, authorization, and
destination, then CASes `commit_started` immediately before irreversible mutation/publication. Cancellation
before that CAS wins; after it returns `commit_in_progress` and never claims cancellation. A verified commit
publishes `succeeded`; late output after a tombstone is discarded. Profiles that cannot prove bounded disposal
are rejected from async execution, preventing permanent worker capture. No terminal result is overwritten.

Artifacts are private and content-addressed by digest with opaque id, owner/workspace/job, media type, size,
created/expiry times, and verified checksum. They expose no path. `export_job_artifact` rechecks ownership,
retention, digest, project confinement, write capability, confirmation, no-clobber/overwrite, and expected
target digest, then verifies and atomically publishes with backup.

### Audit

Async audit events are separate from the `start_job` request event: accepted, started, bounded progress summary,
cancel requested/effective, publication, and terminal. They include ids, state, type, owner fingerprint,
capabilities, input digests, counts, timings, and error codes, never prompts, ontology content, queries, paths,
vendor bodies, credentials, or artifact bytes. A failed pre-commit audit-intent blocks mutation. A terminal
audit failure after a real commit leaves `succeeded` with `audit_incomplete=true`; it is not retryable failed and
the commit is never repeated.

## Consequences

- A generic start tool does not imply generic authority.
- Read-only computation can finish without mutation, but every externally visible publication remains fenced.
- Crash recovery is deliberately not claimed in 0.8.0; exported verified artifacts are the persistence boundary.

## Verification

- Fake clocks/executors and barriers cover every legal/illegal transition, idempotency, quotas, retention,
  queue rejection, fairness, progress ordering, owner mismatch, and restart.
- Deterministic races stop at compute, staging, permit acquisition, ontology/file commit, cache insert, artifact
  export, terminal publication, and audit; cancel/revoke/expiry/close/shutdown is raced at every point.
- A non-interruptible fake reasoner proves async rejection; a delayed-but-bounded fake proves `cancel_pending`,
  late-result discard, and absence of cache/artifacts.
- Broker tests use two principals and two windows and prove job ids cannot route or leak across either boundary.
