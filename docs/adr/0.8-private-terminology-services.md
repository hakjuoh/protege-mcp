# 0.8 OntoPortal profile and owner-bound terminology services

- Status: accepted
- Date: 2026-08-18
- Amended: 2026-08-19

## Context

The 0.8.0 external-term workflow shipped one OLS4 adapter. M8B adds the common OntoPortal API surface
without weakening the existing evidence, cache, credential, and egress contracts. BioPortal and AgroPortal
implement the same reviewed route and response family, while their deployed endpoints and exact upstream
revisions differ.

Project policy remains untrusted routing input. It may select an owner alias and credential identifier, but
cannot provide an origin or secret.

## Decision

### Released registry profiles

`ExternalTermProviderRegistry` is the only runtime profile resolver. It registers `ols4` and `ontoportal`;
lookup of any other value fails with `provider_profile_unsupported` before owner credential, cache, or
network access.

BioPortal and AgroPortal are not profile names. They are Preferences presets that fill the editable origin
with `https://data.bioontology.org` or `https://data.agroportal.eu`. A compatible custom deployment uses the
same `ontoportal` profile with its own exact HTTPS base URL.

One adapter implements behavior proven by both independently maintained fixture sets. Neither deployment
publishes a stable version identifier on this surface, so compatibility is pinned independently to official
source commits `ncbo/ontologies_api@1c59646038f6dd8b5acde2e11ae62dc7a990e801` and
`agroportal/ontologies_api@e0dcb4f741d13bb476b754220d2c7051da867c06`. The fixtures are sanitized
representative documents derived from those contracts rather than claims of live captures. Unknown language
is `und`, absent optional metadata stays absent, and search scores are deterministic positional scores rather
than vendor relevance scores.

No FHIR terminology-server profile or liveness reservation is exposed. Supporting a different protocol or
identity model requires a separate reviewed adapter and policy contract.

### Owner configuration and Preferences

**Preferences → MCP → Externals** edits two independent collections:

- exact origin aliases with profile and HTTPS base URI; and
- credential bindings with credential id, provider id, origin alias, authentication scheme, constrained
  header or query parameter placement, and optional project fingerprint.

This preserves multiple provider/project-scoped credentials for one origin. Secret values are separate
owner-only `<credential-id>.cred` records, never JSON or project policy fields. Applying changes coordinates
secret rotation/deletion and metadata replacement under one owner lock and attempts rollback on failure.
Failures are surfaced without discarding unrelated server preferences. A malformed or unreadable provider
store disables only the Externals editor; opening Preferences creates no provider state.

The local-owner **Test Connection** action uses the production HTTPS transport: exact-origin confinement,
DNS resolution and address-class validation, pinned-address TLS, bounded redirects/retries/body size,
credential reopening, response canaries, and query-free source evidence. It is a local configuration action,
not a project operation. Only one probe may run per Preferences panel; timeout and disposal cancel the
panel-owned attempt, wipe temporary secret material, and prevent queued-worker starvation. Loopback origins
display and require confirmation of their test-only private-address exemption.

### Authentication and egress

- OLS4 is tested anonymously.
- `ontoportal_api_key` stores only the key and constructs the documented
  `Authorization: apikey token=<key>` value.
- `query_api_key` supplies the documented `apikey` query parameter only at the final HTTPS transport
  boundary and strips it from evidence, cache identity, errors, and logs.
- Generic `bearer` is restricted to `Authorization`; generic `api_key` is restricted to its API-key header.
- Authenticated redirects are rejected. Redirects, retries, cache authority, credential rotation/deletion,
  and response redaction retain the existing security contract.

OntoPortal search and inspection pin JSON output and explicitly use the common `include`, `format`, `page`,
`pagesize`, `include_views`, `display_context`, and `display_links` parameters where applicable.
`download_format` remains endpoint-scoped and is not sent because M8B performs no ontology downloads.

## Consequences

- Policy, runtime results, and cache partitions expose one stable `ontoportal` profile.
- BioPortal and AgroPortal remain independently testable compatibility presets without duplicating adapters.
- Users may connect any compatible deployment by editing the preset-populated HTTPS origin.
- Owner GUI edits preserve the complete origin/credential model and use the hardened transport for probes.
