# 0.8 reasoner capabilities and materialization

- Status: accepted for implementation
- Date: 2026-07-20

## Context

Installed reasoners vary in OWL coverage, SWRL support, built-ins, incremental behavior, and explanations.
Existing inferred snapshots are internal bounded projections and cannot be relabelled as a public complete
materialization. A public workflow needs exact capability evidence, non-executing rule validation, whole-category
bounds, provenance, preview, and environment-specific commit semantics.

## Decision

### Capability vocabulary

Every capability is one of `supported`, `unsupported`, `unknown`, or `untested`, with source/evidence and
caveats. Profiles are keyed by one exact reviewed tuple of factory id/class SHA-256, a digest of every
class (including inner classes) in explicit reasoner/OWLAPI/compatibility package scopes, the scope class
count, implementation version, configuration-class SHA-256, semantic configuration digest, and effective
buffering mode. Every HermiT tuple attests Apache Axiom, and both replacement layouts attest AutomataLib.
Base and multi-release variants plus their activation markers are in the digest. Only containers declaring
`Multi-Release: true` activate versioned entries, and effective class-loader bytes must match the exact
active JVM candidate.
Effective class-loader resources must match the scanned class set, so split-package overrides cannot
retain a reviewed tuple. Felix `bundle:` resources are normalized through the trusted framework local-URL
bridge and rechecked as bounded local files or JARs. `jar:file:` fields are parsed directly without
invoking their URL handler; remote protocols, file authorities, UNC paths, and arbitrary URL handlers
are rejected before filesystem access. Independent
allowlists are never combined into untested tuples. Reviewed 0.8
profiles cover HermiT `1.3.8.431`, OWLAPI structural reasoner `4.5.29`, and ELK `0.5.0`
with factory id `org.semanticweb.elk.owlapi.ElkReasonerFactory` plus the separately attested official
Protege bundle ids `au.csiro.elk.reasoner.factory` and
`org.semanticweb.elk.elk.reasoner.factory`. Every other version is `unknown`; name
matching never borrows another version's profile.

The complete configuration digest includes OWLAPI policies, timeout/monitor identity, bounded public
configuration state, and explicitly serialized ELK worker and evictor-builder values. A second semantic
digest excludes reviewed operational-only timeout, worker, monitor, and evictor fields so those settings do
not change OWL/SWRL capability claims. ELK unsupported-feature and incremental-mode settings remain semantic;
both official buffering recommendations are separate exact tuples. The official Protege HermiT adapter's
`ignoreUnsupportedDatatypes=true` variant is reviewed separately from factory default. Uninspectable or
non-reviewed semantic state remains `unknown`, even when factory and version otherwise match.

The report covers OWL profile/construct families, SWRL, every predicate in a closed pure built-in allowlist,
DL-safety, incremental update,
consistency/satisfiability, hierarchy/types/property assertions, explanations, cancellation, and known
incompatibilities. `validate_rules` parses but never executes every atom, variable, and built-in. Built-ins not
on the reviewed pure allowlist, including plugin-defined filesystem/network/side-effecting built-ins, are
`unsupported` for validation and materialization. Per-rule output separates the necessary non-built-in
body-variable binding check from DL-safety engine evidence; OWLAPI rule syntax does not identify a non-DL
predicate partition and therefore is not presented as a formal syntactic proof.

Validation accepts at most 128 source ontologies, 4,096 characters per ontology/version identifier,
2,000 rule occurrences/unique rules, 512 combined atoms
and 256 annotations in one rule, 20,000 total atoms, 100,000 total arguments, 262,144 characters/4,096
nodes/128 levels per canonical object, 2 MB of canonical UTF-8, and 10 seconds of capture work. Crossing any
bound fails before a partial result. The model-thread hop traverses direct imports under the source cap and
copies only bounded ontology/version identities and immutable rule axioms; bounded canonicalization runs off
that thread and produces a detached DTO. Continuation
pages require the prior snapshot token, which binds the complete selected source set, canonical rules,
capability digest, vocabulary, and identity. Every response also contains bounded summaries of all
incompatible rules, while detailed pages remain below the 8 MiB headless transport ceiling.

### Categories and preview

The closed materialization categories are subclass/equivalent-class axioms, class assertions, property
hierarchy axioms, and object/data property assertions. Requests name exact categories and per-category/global
count/byte/time bounds. An unsupported or unknown requested category is an error. If enumeration errors or a
bound is crossed, that category is discarded in full and the preview is an error. A result never presents a
partial category or omitted category as complete.

Computation uses one immutable isolated workspace and disposable reasoner. `materialize_inferences` is the
read-only preview tool and creates a private verified artifact plus `MaterializationReport`;
`commit_materialization` is the only mutating tool and accepts the same owner-scoped artifact from synchronous
preview or a job. Previews expire after 30 minutes and use job artifact quotas/cleanup. Preview does not change
the live reasoner, ontology, mapping store, or filesystem destination. It does populate the owner-private,
bounded artifact store and may populate validated runtime-evidence caches. The report distinguishes
requested/supported/produced/skipped,
includes exact input/reasoner identities, counts/truncation, asserted collisions, destination plan, and digest.
One computation remains exclusively fenced until both its worker and bounded reasoner disposal terminate;
cancel-before-start and late-result paths cannot release the service early or publish an artifact. Cleanup
submission failure or a permanently blocked disposal leaves that service fail-closed busy rather than
allowing undisposed reasoners to accumulate.

### Commit and provenance

The default destination is a new ontology or project file. Writing the active source requires explicit
`allow_source=true` and policy permission. Commit consumes the preview fingerprint and, under the job/synchronous
commit permit, rechecks revision, closure/imports, mappings, policy/assets, reasoner configuration,
authorization, confirmation, cancellation, destination state, and artifact digest.

The plugin applies every axiom batch in one model-manager broadcast. Active-source changes form one Undo unit;
a new ontology is created through Protégé's model-manager lifecycle and reports that ontology creation itself
is not a single Undo operation. The headless adapter uses advisory project lock, verified
serialization, temporary reparse/digest, guarded no-overwrite hard-link publication, and backup.
Merge/overwrite is explicit; identical
axioms are idempotent and asserted/inferred collisions are disclosed before commit. Generated axioms use a
stable provenance IRI derived from source/reasoner/category/content digests. Timestamp and job/preview id live in
report/audit, not axiom identity. Exact logical axiom + provenance-id pairs are no-ops in reject/replace mode
only when no alternate-provenance form remains in the destination document; explicit merge may no-op while
retaining alternates. Imported duplicates are not local matches. Different provenance is an explicit
merge/replace collision. The source ontology is never the implicit
destination.

Commit requires both ontology administration and curation authority. Headless publication additionally
requires project read/write authority. Project-file operations use secure directory-relative handles where
available; the pathname fallback is allowed only for a stable, private POSIX ancestor chain and otherwise
fails closed. Staged content is forced before guarded publication, and transaction-directory entries receive
a best-effort directory force on platforms that support it. A provider that cannot expose a forceable file
channel, owner-only private directory, or same-filesystem hard link is rejected. A sticky shared ancestor such
as `/tmp` is allowed only above an already non-shared-writable project directory; a target directly in a
shared-writable directory is rejected. Providers without POSIX attributes, including the normal Windows
provider, fail closed. Other processes/plugins running as the same account remain trusted. Recovery runs only
under the authenticated project-local lock in a non-shared-writable project root and accepts exact-owner
`0700`, UUID-named directories with a
single state known to precede publication may restore its displaced inode. Publication-uncertain, completed,
recovery-uncertain, or multiple/mixed candidate states never restore an absent target automatically. Recovery
marks uncertainty before linking and removes `displaced` before clearing state markers. A recovery or cleanup
side effect stops the materialization attempt with a fact-granular receipt and requires retry. File forcing is
mandatory and directory forcing is best effort, so power-loss durability is not claimed.

## Consequences

- Honest unknown/untested states are preferable to optimistic inference from a reasoner name.
- Internal QC/SPARQL projection helpers may be reused only after their category-atomic bounds and provenance
  satisfy this contract; their old behavior is not public materialization evidence.
- Materialization can run synchronously or as the 0.8 job type while sharing one core request/result contract.
- A cooperating reader can observe the brief move-to-link absence interval. Locked transaction startup can
  restore one unambiguous pre-publication orphan; ambiguous evidence requires operator resolution when the
  bounded quota is reached.

## Verification

- Exact HermiT/structural/ELK fixtures cover the official Protege HermiT adapter, runtime-code scopes,
  semantic versus operational configuration changes, hierarchy/assertion/property-chain/consistency/
  satisfiability/incremental behavior, unsupported built-ins, DL-safety, and no-execution validation.
- The six-category live fixture covers successful enumeration and whole-category overflow. Core fixtures cover
  unsupported/unknown profiles, empty requests, enumeration failure, deterministic rerun, quota eviction,
  consistency gating, and a non-cooperative reasoner hard timeout with late-result fencing.
- Live tests prove preview changes nothing, model-manager ontology creation, one-Undo active-source commit,
  stale no-op refusal, source confirmation, alias rejection, and external-policy refusal. Headless tests cover
  verified atomic output, idempotence, provenance collision handling, unrelated-axiom preservation on replace,
  symlink refusal, source/destination drift, final-publication races, locked crash-orphan restoration,
  post-publication ambiguity, hostile retained entries, multiple/mixed-orphan refusal, divergent lock roots,
  and a separate JVM halted after its recovery link.
- Two identical runs prove stable axiom identity/no duplicate provenance, while a changed source/reasoner digest
  requires explicit collision handling.
