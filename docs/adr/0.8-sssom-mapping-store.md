# 0.8 SSSOM mapping store and reuse proposals

- Status: accepted for implementation
- Date: 2026-07-20

## Context

SSSOM mappings are governance/interchange records, not OWL equivalence axioms. They need lossless extension
round trips, a stable authoritative location, and revision-safe mutations across the live and headless adapters.
Protégé Undo cannot honestly cover a filesystem sidecar, so mapping revision and recovery must be explicit.
External term proposals also need a defined handoff without reintroducing an implicit mutation.

## Decision

### Format and store

0.8.0 supports SSSOM 1.0 TSV. The canonical store is the policy-v2 `mappings.path`, defaulting to
`.protege-mcp/mappings.sssom.tsv` under the canonical project root. It is never synthesized into ontology
axioms. The store is UTF-8, canonical LF/no-BOM on newly generated output, deterministic metadata/header/row
order, and subject to fixed byte, row, column, and cell limits.

Path reads bind captured file identity to an owner-only hard-link snapshot in a writable directory on the
same filesystem. The search starts at the source parent and its ancestors, then uses the system temporary
directory only when it is on that filesystem. This supports read-only source directories without an ABA
window. Filesystems unable to provide the snapshot fail closed; adapters may instead supply bytes after their
own trusted capture to the same bounded parser.

All standard supported fields and every unknown extension column retain their original string and row affinity.
Unknown columns survive read/edit/write. Formula-looking cells are preserved and reported as warnings; an
explicit `spreadsheet_safe` export escapes them and labels the output non-lossless. CURIEs resolve only through
the file prefix map and policy-approved prefixes.

### Identity and concurrency

`MappingRecord` has a stable `mapping_id`. Imported rows without one receive a deterministic SHA-256 id over
normalized subject, predicate, object, justification, author, and source. Exact duplicate records are
idempotent; the same id with different content is a conflict. The full canonical store has a SHA-256
`mapping_revision` independent from the ontology revision.

Every mutation supplies the expected mapping revision. Both live and headless adapters take the same project
advisory lock before rechecking it, so a plugin/CLI race has no check-then-write gap. Writes parse and validate
the full candidate, write a confined temporary file, fsync where available, reparse and verify its digest, then
atomically
replace with backup/recovery. A stale revision, failed lock, invalid candidate, or failed replacement changes
nothing. Mapping writes require confirmation and filesystem/project capabilities; they are not on GUI Undo.
File import re-resolves the source beneath the canonical project root and takes its stable hard-link snapshot
inside that same lock hold before the mapping CAS; adapter preflight paths alone never authorize source bytes.
The mutation guard is checked both immediately before and immediately after atomic replacement, so ontology,
policy, or live authorization drift around the rename triggers verified recovery of the prior store.

The advisory lock is the inter-process protocol for cooperating Protégé MCP adapters; it cannot prevent an
unrelated process that deliberately ignores the lock from writing the same file. Every source read is nevertheless
bound to the parser's same-filesystem hard-link snapshot and rechecks canonical project ancestry, raw bytes, and
parent identity. Destination parent directories must already exist, which avoids check/create symlink races. A
durable private recovery copy exists before replacement, and successful commits retain only the latest verified
backup per target. Parseable but semantically invalid stores may be repaired only by revision-pinned `replace`;
add, remove, and merge remain fail-closed. Syntactically unreadable stores require explicit manual recovery.

### Predicates and validation

The accepted base predicates are the SSSOM 1.0 mapping-predicate vocabulary and a policy-v2 allowlist.
SKOS mapping predicates keep their mapping meaning and are never converted to OWL equivalence. Symmetric
exact/close/related/equivalence predicates are undirected: reverse pairs and self maps are not cycles.
Directional broad/narrow predicates normalize to narrow-to-broad edges; only SCCs of two or more distinct terms
are cycles, governed per predicate by v2 `allow|warning|error` (default `error`). Many-to-one restrictions apply
only to policy-named predicate and subject-ontology/provider/target scopes. Malformed ids and conflicting exact
mappings block mutation. Missing
or deprecated entities and source/license violations block when their policy rule is required and otherwise
produce stable findings.

### Independent SSSOM-Java compatibility review

The implementation was compared against the locally checked-out `sssom-java` 1.11.3 line as an
interoperability reference. That project is GPL-3.0-or-later, while this project is BSD-2-Clause, so it is
not linked, shaded, vendored, or copied. The implementation here is independently written from the SSSOM
format contract and observed reference behavior. A compatible license or explicit linking exception would
be required before reconsidering it as a runtime dependency.

The comparison resulted in these 0.8 behaviors:

- all eight SSSOM built-in prefixes are available without declarations and cannot be redefined;
- structural validation accepts arbitrary declared mapping predicates, while policy v2 may deliberately
  restrict them to the base vocabulary plus its allowlist;
- pipe-separated list slots honor escaped pipes and backslashes;
- `extension_definitions` are validated for identifiers and declared scalar types, while undefined
  extension metadata/columns still round-trip losslessly as required by this ADR;
- set-level propagation follows the SSSOM whole-column rule: it applies only when no mapping row defines
  that slot;
- generated mapping ids normalize expanded identity references, but retain the PLAN-required SHA-256
  `mapping_id` contract instead of adopting SSSOM 1.1 `record_id` or another library's hash format; and
- blank TSV rows and spreadsheet-padded metadata comments are accepted, while canonical output remains
  strict UTF-8 TSV with LF endings.

SSSOM 1.1 slots, JSON/CSV input, external YAML metadata files, inversion, condensation, automatic cardinality
inference, and compatibility conversion of obsolete schemas are not imported into the 0.8 surface. They are
outside the accepted SSSOM 1.0 TSV contract. A 1.1 declaration is an unsupported-version finding; unknown
columns remain available as lossless extensions rather than being silently discarded.

`import_sssom` is all-or-nothing with explicit `replace` or `merge`; there is no implicit upsert. `export_sssom`
writes a confined destination with project-write capability and confirmation, no-clobber by default, and
explicit overwrite plus expected target digest. It takes the project lock, rejects symlinks, reparses output,
and atomically replaces with backup. `list_mappings` and validation use deterministic ordering and cursor-based
pagination. Plugin and headless adapters use the same core parser, validator, canonicalizer, ids, and findings.

All mapping tools are registered for policy v1/v2 and, on the live Protégé surface, no-policy projects. V2 uses
its declared/default store and governance. V1 requires an explicit path beneath its canonical project root and
applies structural validation without v2-only governance. With no policy, the live adapter requires an explicit
path beneath the active document directory and unrestricted local-admin compatibility; headless always requires
a valid project policy. Invalid policy or restricted mode fails closed.

### Reuse proposals

`propose_term_reuse` creates no ontology or sidecar mutation. It stores an immutable, memory-only 15-minute
`ReuseProposal` scoped to exact principal/grant, workspace, provider-result fingerprint, model/input identity,
policy digest, action, and normalized suggested operations. Actions are `reuse_iri`, `add_mapping`, and
`mint_local_with_mapping`.

`accept_reuse_proposal` re-resolves every term and rechecks proposal expiry, model/mapping revisions, policy,
authorization, confirmation, and QC. `reuse_iri` is non-mutating and `add_mapping` is one CAS.
`mint_local_with_mapping` is a two-step saga: ontology commit returns its new revision and signed continuation,
then mapping CAS binds to that receipt and original mapping revision. A failed second step reports `partial`,
leaves the minted term, and returns a bounded retry/manual-recovery continuation; it never claims atomicity or
rolls back a later edit. Proposals expire after 15 minutes and are capped at 64/principal, 256/backend, and
256 KiB each; revocation/close/restart removes them. There is no implicit MIREOT import, automatic mint
suppression, lifecycle state, or hidden mapping write.

## Consequences

- Mapping-aware impact/QC can cite a stable mapping revision without changing ontology fingerprints.
- A two-resource mint-and-map workflow exposes its intermediate state and recovery instructions instead of
  claiming a transaction Protégé cannot provide.
- Policy v1 projects retain their exact digest and use the explicit confined-path contract above; policy v2 is
  required for a governed default store.

## Verification

- Fixtures cover all supported fields/extensions, BOM/CRLF/Unicode/quoted tabs/newlines, formulas, CURIEs,
  duplicates, id collisions, conflicts, cycles, licenses, deprecated/missing terms, limits, and round trips.
- Barrier tests race two writers, source swaps, lock failure, failed fsync/replace, cancellation, and shutdown;
  only one expected revision commits and recovery always yields a valid old or new store.
- Cross-surface fixtures assert byte-identical canonical output, record ids, revisions, findings, and error codes.
